### Foundations

#### Week 1 — Software Development Processes

| Term | Definition | Source |
|---|---|---|
| [**Software engineering**](chapters/week-01-software-development-processes.html) | **Software engineering** is the application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software. | IEEE Standard Glossary of Software Engineering Terminology, quoted on L1 slide 13 |
| [**software process**](chapters/week-01-software-development-processes.html) | A **software process** is the structured set of activities a team follows to develop, operate, and maintain software — typically requirements, design, implementation, testing, deployment, and maintenance. A process model prescribes how those activities are arranged, for example Scrum's iterative sprints with feedback loops. | cf. IEEE definition of software engineering, L1 slides 13, 22–24 |
| [**software development life cycle**](chapters/week-01-software-development-processes.html) | The **software development life cycle (SDLC)** is the full life of a software product, from initial conception through development, deployment, and operation, to maintenance and eventual retirement. A software process describes how the team organizes work across those life-cycle phases. | cf. L1 slides 13, 22, 26 |
| [**software crisis**](chapters/week-01-software-development-processes.html) | The **software crisis** is the 1960s mismatch between what software projects delivered and what was needed: its impact was on time, cost, and quality. The response — R&D in software engineering — produced the sub-fields this course teaches: software development process models, software architecture, design principles, testing methods, and design patterns. | L1 slide 13; Dijkstra, The Humble Programmer (EWD340 |
| [**Software Crisis 2.0**](chapters/week-01-software-development-processes.html) | **Software Crisis 2.0** (1970–now) is the second software crisis, driven by abundance rather than scarcity: push factors (advances in hardware, reductions in hardware costs, increases in processing power, device proliferation, an effectively infinite amount of data available) and pull factors (digital natives consuming technology) create lots of data and lots of computation. Named responses include parallel processing, cloud computing, data analytics, security, IoT, edge computing, DevOps, CI/CD, and microservices. | L1 slide 14, after Fitzgerald, Software Crisis 2.0 (IEEE Computer, 2013 |
| [**cloud service models**](chapters/week-01-software-development-processes.html) | The **cloud service models** — IaaS, PaaS, and SaaS — differ in how much of the stack the vendor manages: **IaaS** rents raw infrastructure (e.g., AWS, Google Cloud); **PaaS** hosts your application on a managed platform (e.g., AWS Elastic Beanstalk, Heroku); **SaaS** delivers a finished application (e.g., Google Apps, Salesforce). | L1 slide 17 |
| [**Cloud-enabled**](chapters/week-01-software-development-processes.html) | **Cloud-enabled** describes legacy enterprise applications designed for local data centres but modified to run on the cloud, retaining most of their original features — as opposed to cloud-native applications, which are built for cloud environments from the start. | L1 slide 17 |
| [**Open-content**](chapters/week-01-software-development-processes.html) | **Open-content** is material — text, media, datasets — that others may legally copy, modify, and redistribute; it is the data-side sibling of open-source (code you may inspect) and the opposite of closed-source (code you cannot). | L1 slide 16; e.g., Wikipedia's articles |
| [**Embedded software**](chapters/week-01-software-development-processes.html) | **Embedded software** is software that runs inside a dedicated device and interacts directly with the hardware it controls or senses — the "embedded & edge" deployment mode, e.g., a smart-home camera's local motion detection or an industrial control system. | L1 slide 16; Tutorial 1 applications A and D |
| [**real-time**](chapters/week-01-software-development-processes.html) | A **real-time** system must respond to stimuli within strict timing constraints — a late answer is a failed answer, e.g., software controlling machinery in a manufacturing plant. | L1 slide 16; Tutorial 1 application D |
| [**concurrent**](chapters/week-01-software-development-processes.html) | A **concurrent** system handles many users or operations at the same time, e.g., a global streaming platform accessed by millions of users concurrently. | L1 slide 16; Tutorial 1 application B |
| [**distributed**](chapters/week-01-software-development-processes.html) | A **distributed** system's components run on multiple networked machines and coordinate over the network, e.g., cameras that process motion locally while cloud services store video and send notifications. | L1 slide 16; Tutorial 1 application A |
| [**Scrum**](chapters/week-01-software-development-processes.html) | **Scrum** is an agile software process built on iterative development with feedback loops: work happens in fixed sprints, opened by sprint planning, and each sprint ends with a working increment that generates feedback — enabling quick response to changes. | L1 slide 23 |
| [**sprint**](chapters/week-01-software-development-processes.html) | A **sprint** is one fixed-length iteration of Scrum: sprint planning picks the top-priority items from the product backlog, the team designs, builds, and tests them, and the sprint ends with a working increment (+ demo & feedback). | L1 slide 23 |
| [**product owner**](chapters/week-01-software-development-processes.html) | The **product owner** is the Scrum role accountable for the product backlog — the product vision and the ordering of its priorities — e.g., reprioritizing the backlog after a sprint demo revealed new needs. | L1 slide 24; Quiz 1 Q6 |
| [**Deployment**](chapters/week-01-software-development-processes.html) | **Deployment** is the process between the acquisition of software and its execution — the activities that make the software available for use after development. Deployment decisions affect quality attributes such as availability, performance, security, usability, interoperability, reusability, scalability, portability, and maintainability. | L1 slide 26, after Humble & Farley, Continuous Delivery |
| [**Bare metal**](chapters/week-01-software-development-processes.html) | **Bare metal** deployment runs applications directly on the hardware, on top of only a host OS: complete control and physical isolation are the upside; potentially wasted hardware resources, cost, scalability issues, and reduced developer productivity are the price. | L1 slide 31 |
| [**virtual machine**](chapters/week-01-software-development-processes.html) | A **virtual machine (VM)** is a full software computer — its own guest OS — running on a hypervisor above the host OS and hardware. VMs improve resource utilization (reduced cost, flexibility, scalability), but a full OS still runs inside each VM, VMs are susceptible to side-channel attacks, and the "noisy neighbour" problem appears when workloads share hardware. | L1 slide 32 |
| [**Serverless**](chapters/week-01-software-development-processes.html) | **Serverless** is a cloud-native development model in which there are still servers — developers and enterprises just don't manage them: developers package the code in containers, the platform deploys the application in those containers and scales it automatically with demand, and economics are metered on demand (no cost when idle), e.g., AWS Lambda. | L1 slide 37 |
| [**serverless function**](chapters/week-01-software-development-processes.html) | A **serverless function** works on Function-As-A-Service (FAAS) with an event-driven execution model: the provider manages the physical servers and dynamically allocates resources, the function runs when needed, and it is stateless and ephemeral with short execution times — e.g., batch processing of images and video, scheduled data compression. | L1 slide 38 |
| [**deployment pipeline**](chapters/week-01-software-development-processes.html) | A **deployment pipeline** is an automated implementation of the application's build, deploy, test, and release process; a CI/CD pipeline is the automated workflow that enables teams to build, test, and deploy code efficiently and reliably. | L1 slides 39–40 |
| [**Continuous delivery**](chapters/week-01-software-development-processes.html) | **Continuous delivery** ensures that every good build is potentially ready for production release — software can be released into production at any given time. | L1 slides 41–42 |
| [**Continuous deployment**](chapters/week-01-software-development-processes.html) | **Continuous deployment** automates the release of a good build into the production environment — code changes are released automatically into production. | L1 slides 41–42 |
| [**In-place deployment**](chapters/week-01-software-development-processes.html) | **In-place deployment** stops each running module/compute, installs the latest version, then starts and validates it: minimal disturbance to the infrastructure and reduced infrastructure cost, but availability suffers while the unit is down (e.g., AWS Beanstalk's one-at-a-time, half-at-a-time, all-at-once mechanisms). | L1 slide 43 |
| [**Rolling deployment**](chapters/week-01-software-development-processes.html) | **Rolling deployment** replaces the previous version by completely replacing the infrastructure it runs on — e.g., containers running the old version replaced one-by-one by containers running the new version. There is no isolation between old and new versions, which complicates rollback. | L1 slide 43 |
| [**Canary deployment**](chapters/week-01-software-development-processes.html) | **Canary deployment** reduces the risk of deployment by incrementally deploying the new version, starting with a small subset of users (a.k.a. incremental rollout) — a variant of blue-green deployment that can double as A/B testing. | L1 slide 45 |
| [**site reliability engineer**](chapters/week-01-software-development-processes.html) | A **site reliability engineer (SRE)** improves customer experience by creating software that improves the reliability of systems in production — fixing issues, responding to incidents, and taking on-call responsibilities, rather than only building new features. | L1 slide 48 |

#### Week 2 — Modern Software Engineering

| Term | Definition | Source |
|---|---|---|
| [**CI/CD**](chapters/week-02-modern-software-engineering.html) | **CI/CD** is the pairing of two delivery practices: **continuous integration (CI)** — developers integrate code into a shared repository several times a day, each check-in verified by an automated build so problems are detected early — and **continuous delivery/deployment (CD)** — every good build is kept potentially ready for production release (delivery), or released automatically into production (deployment). | L1 slides 41–42 |
| [**DevOps**](chapters/week-02-modern-software-engineering.html) | **DevOps** is a set of software development practices that combines software development (Dev) and operations (Ops), intending to reduce the time between committing a change and that change running in normal production, while ensuring high quality. | L1 slide 46, after Ebert et al., IEEE Software 2016 |
| [**Containerization**](chapters/week-02-modern-software-engineering.html) | **Containerization** is packaging an application together with only the OS processes and dependencies it needs, so it runs identically on any host that runs a container engine — lighter than a virtual machine, which carries a full guest OS. | L1 slides 32–33 |
| [**Blue-green deployment**](chapters/week-02-modern-software-engineering.html) | **Blue-green deployment** is a release strategy that shifts traffic between two identical environments running different versions of the application, achieving near-zero downtime and easy rollback. | L1 slide 44 |
| [**Vibe coding**](chapters/week-02-modern-software-engineering.html) | **Vibe coding** is building software primarily by prompting AI — compressing the distance from idea to prototype, requirement to interface, and prompt to implementation — while accepting weaker architecture, quality, and a larger verification burden. | L2 slide 11 |
| [**Automation**](chapters/week-02-modern-software-engineering.html) | **Automation** (AI mode) is the mode where AI handles repeated tasks whose steps are already known — automating them efficiently and reliably, every time (e.g., workflow automation such as CI/CD and infrastructure deployment). | L2 slide 3 |
| [**Pattern detection**](chapters/week-02-modern-software-engineering.html) | **Pattern detection** (AI mode) is the mode that exploits rule-like structure in tasks: AI sifts through a gigantic codebase to detect vulnerabilities — e.g., identifying query patterns, or the repeating library-usage pattern behind a vulnerability. | L2 slide 3; Quiz 1 Q1 |
| [**Collaboration**](chapters/week-02-modern-software-engineering.html) | **Collaboration** (AI mode) is turn-by-turn development: the AI offers suggestion, discussion, and refinement with humans, who review each step as it happens — e.g., code sequence prediction and generation, brainstorming code solutions, and rapid prototyping (Copilot, Copilot Chat). | L2 slides 3–4 |
| [**Delegation**](chapters/week-02-modern-software-engineering.html) | **Delegation** (AI mode) moves the human review to the final output: the engineer states the desired outcome and the AI plans, executes (updating files, testing, fixing bugs, iterating), and presents the result for review — you review the final output, not the steps (e.g., Claude Code, Cursor). | L2 slide 3 |
| [**Orchestration**](chapters/week-02-modern-software-engineering.html) | **Orchestration** (AI mode) coordinates several specialized agents in several roles: AI handles task decomposition, planning, and execution, while a human or an AI coordinates (e.g., CrewAI, LangGraph). | L2 slide 3 |
| [**Predictive analytics**](chapters/week-02-modern-software-engineering.html) | **Predictive analytics** estimates a numeric likelihood or outcome from historical data — e.g., which component is most likely to fail in production, or which requirements are likely to be implemented successfully. Unlike pattern detection, it estimates likelihoods rather than matching usage patterns. | Quiz 1 Q1; L3 slide 34 |
| [**Garbage in, garbage out**](chapters/week-02-modern-software-engineering.html) | **Garbage in, garbage out (GIGO)** is the AI risk that output is only as good as your input: models can regurgitate bad code (more applicable to niche use cases), and correctness is not guaranteed — which reduces trust. | L2 slide 10 |
| [**Technical debt**](chapters/week-02-modern-software-engineering.html) | **Technical debt** is the accumulated cost of shortcuts taken in code and design. Maintaining others' code is hard; maintaining automatically generated code is harder — so AI-assisted coding can increase technical debt. | L2 slide 10 |
| [**Autonomous development**](chapters/week-02-modern-software-engineering.html) | **Autonomous development** is end-to-end software development carried out by LLM-based agents. It requires: access to tools and data; the ability to perform actions (e.g., retrieve an issue description); collaboration with and delegation of tasks to other agents; tracking of long-running tasks; and exchange of results in a predictable format. | L2 slide 12 |
| [**MCP**](chapters/week-02-modern-software-engineering.html) | **MCP (Model Context Protocol)** standardizes how an AI application discovers and uses external tools — e.g., VS Code + Copilot connecting through an MCP connector to a GitHub MCP server exposing Git operations, files in the repo, and GraphQL APIs. | L2 slide 12 |
| [**A2A**](chapters/week-02-modern-software-engineering.html) | **A2A (Agent-to-Agent protocol)** standardizes communication between independent AI agents. | L2 slide 12 |

#### Week 3 — Requirements

| Term | Definition | Source |
|---|---|---|
| [**requirement**](chapters/week-03-requirements.html) | A **requirement** is a condition or capability needed by a user to solve a problem or achieve an objective, or a condition or capability that must be met or possessed by a system to satisfy a contract, standard, specification, or other formally imposed document — or a documented representation of either. | IEEE, quoted on L3 slide 3 |
| [**functional requirement**](chapters/week-03-requirements.html) | A **functional requirement (FR)** specifies something the system should do — typically a behavior or function, e.g., "The passenger shall be able to print boarding passes for all flight segments for which she has checked in." | L3 slide 9 |
| [**non-functional requirement**](chapters/week-03-requirements.html) | A **non-functional requirement (NFR)** describes a constraint on the system or its development that is not directly related to specific functionality — it describes how well the system works, e.g., "Mean time between failure ≥ 9000 hrs." | L3 slide 9 |
| [**quality attribute**](chapters/week-03-requirements.html) | A **quality attribute** is a property of the system — such as performance, scalability, security, or usability — that contributes to its quality; a combination of quality attributes defines the software quality, and they are usually stated as non-functional requirements. | L3 slide 10 |
| [**requirement trade-off**](chapters/week-03-requirements.html) | A **requirement trade-off** is a design situation in which improving one quality attribute degrades another — e.g., adding redundant checks and backups improves reliability but makes the system slower and costlier — forcing prioritization under resource constraints. | L3 slide 23 |
| [**product backlog**](chapters/week-03-requirements.html) | A **product backlog** is the ordered list of a product's requirements, each with a type, a unique identifier, a description, a priority, and a planned sprint; it allows work allocation, developing test specifications, and design development. | L3 slides 7, 26 |
| [**Requirements elicitation**](chapters/week-03-requirements.html) | **Requirements elicitation** discovers requirements — e.g., by interview, workshop, document analysis, or prototyping. | L3 slide 4 |
| [**Requirements analysis**](chapters/week-03-requirements.html) | **Requirements analysis** analyzes, decomposes, derives, and understands requirements, negotiates them, and identifies gaps. | L3 slide 4 |
| [**Requirements specification**](chapters/week-03-requirements.html) | **Requirements specification** produces written and illustrated requirements for comprehension, review, and use. | L3 slide 4 |
| [**Requirements validation**](chapters/week-03-requirements.html) | **Requirements validation** confirms the correct set of requirements — the set that traces back to business objectives and will enable developers to build a solution; corrections feed back into elicitation. | L3 slides 4, 28 |
| [**event-response table**](chapters/week-03-requirements.html) | An **event-response table** is an elicitation source that identifies external stimuli and describes the system's responses to each. | L3 slide 5 |
| [**usage-centric requirement**](chapters/week-03-requirements.html) | A **usage-centric requirement** states a capability from the user's point of view — "As a user, I can upload an image into the system so that I can showcase my photography skills to the world." | L3 slide 6; Quiz 1 Q9 |
| [**product-centric requirement**](chapters/week-03-requirements.html) | A **product-centric requirement** states what the system will do — "The system will support a range of graphic file formats up to 20 mb in size" — and is refined into testable system statements. | L3 slide 6; Quiz 1 Q9 |
| [**Requirement refinement**](chapters/week-03-requirements.html) | **Requirement refinement** decomposes a requirement into child requirements at least two levels deep — from capability ("allow user to register using email/password") to testable rule ("password should contain upper and lower case letters and numbers, minimum length, avoid dictionary attack"). | L3 slides 6, 8 |
| [**software requirements specification**](chapters/week-03-requirements.html) | A **software requirements specification (SRS)** is a traditional textual requirements document that only records what is to be done in the project — unlike the product backlog, it is not by itself a planning tool for sequencing the work. | L3 slide 29 |
| [**Requirement traceability**](chapters/week-03-requirements.html) | **Requirement traceability** gives each requirement a type, a unique identifier, a brief high-level description, a priority, and other information (e.g., sprint-id), and traces it to use-case, design-document, code-module, and test-case references. | L3 slide 26 |
| [**external quality attribute**](chapters/week-03-requirements.html) | An **external quality attribute** is observed when the software is executing and impacts the user's experience — it develops the user's perception of software quality. | L3 slide 11 |
| [**internal quality attribute**](chapters/week-03-requirements.html) | An **internal quality attribute** is not directly observed when the software is executing — it is perceived by the developers and maintainers, and encompasses aspects of design that may impact external attributes. | L3 slide 11 |
| [**Security**](chapters/week-03-requirements.html) | **Security** is the system's ability to resist unauthorized use while still providing its services to legitimate users. Core concerns: confidentiality and integrity; it relies on authentication, authorization, and auditing. Record security requirements early in the product cycle, and make them specific and testable. | L3 slide 14 |
| [**Confidentiality**](chapters/week-03-requirements.html) | **Confidentiality** protects data against unauthorized disclosure or access. | L3 slide 14 |
| [**Integrity**](chapters/week-03-requirements.html) | **Integrity** protects data against unauthorized modification. | L3 slide 14 |
| [**Authentication**](chapters/week-03-requirements.html) | **Authentication** establishes who the user is — e.g., the preferred strategy for resolving forgotten passwords, addressing account lockouts, expiring inactive sessions, and re-authenticating critical transactions. | L3 slide 14 |
| [**Authorization**](chapters/week-03-requirements.html) | **Authorization** decides what an authenticated user is allowed to do. | L3 slide 14 |
| [**Auditing**](chapters/week-03-requirements.html) | **Auditing** records actions so misuse can be detected or investigated — specifying what activity should be logged, at what level of detail, and who should have access to the logs. | L3 slide 14 |
| [**Performance**](chapters/week-03-requirements.html) | **Performance** primarily encompasses the responsiveness of the system; low performance means unhappy users, and in real-time systems it can impact safety. Performance requirements affect the choice of architecture (monolithic vs microservices), design, and deployment, plus hardware and network choices. | L3 slides 15–17 |
| [**Caching**](chapters/week-03-requirements.html) | **Caching** stores frequently accessed data closer to the user — high-speed, typically transient storage holding a subset of the data (e.g., Amazon ElastiCache, Redis) — one approach to improving performance. %%(revisited as a scalability lever in Week 12)%% | L3 slide 18 |
| [**Deployability**](chapters/week-03-requirements.html) | **Deployability** is the ease and speed of getting software to production — software allocated to an environment for execution within a predictable, acceptable amount of time and effort. It is measured by deployment frequency, change failure rate, and MTTR, and is impacted by CI/CD, containerization, DevOps, and architectural decisions such as serverless and microservices. | L3 slide 21 |
| [**Usability**](chapters/week-03-requirements.html) | **Usability** measures the effort required to prepare input, operate, and decipher the output of the software — e.g., average time to specify inputs, number of interactions to get information, time to complete a task, user errors or trials needed, and waiting time. It packs in ease of learning (meaningful messages, verbose prompts, tooltips) and ease of use (customizations, autocompletion, autocorrection, scriptable). | L3 slide 22 |
| [**Reliability**](chapters/week-03-requirements.html) | **Reliability** is the ability of the system to keep working correctly over time. The deck's trade-off table shows the cost: improving reliability by introducing redundant checks, backups, and recovery routines makes the system slower and more resource-hungry, degrading efficiency. | Quiz 1 Q7; L3 slide 23 |
| [**Interoperability**](chapters/week-03-requirements.html) | **Interoperability** is the ability of the system to operate with other systems. The deck's trade-off table shows the cost: improving interoperability by allowing open data exchange and API access can expose the system to more vulnerabilities, weakening security. | Quiz 1 Q7; L3 slide 23 |
| [**Efficiency**](chapters/week-03-requirements.html) | **Efficiency** is how well the system uses its resources — doing its work without waste of time, hardware, or money. It is the attribute that pays for reliability's redundant checks, backups, and recovery routines. | Quiz 1 Q7; L3 slide 23 |
| [**Pair-wise prioritization**](chapters/week-03-requirements.html) | **Pair-wise prioritization** compares requirements (or quality attributes) two at a time to force an order — a prioritization framework for identifying the nice-to-haves, with feasibility taking priority. | L3 slides 23, 25 |
| [**Requirements verification**](chapters/week-03-requirements.html) | **Requirements verification** checks whether you have written the requirements right: the requirements have the desirable properties — completeness, correctness, feasibility, prioritization, unambiguity. It is done informally (peer desk-check, pass-around, walkthrough) or formally (inspection — a formal process with a checklist). | L3 slide 28 |
| [**Requirements management**](chapters/week-03-requirements.html) | **Requirements management** is the loop of collecting initial requirements from stakeholders; analyzing; defining and recording; prioritizing; agreeing on and approving; tracing to work items; querying stakeholders after implementation on needed changes; utilizing test management to verify and validate; assessing the impact of changes; revising; and documenting changes. | L3 slide 32, after IBM |

### Architecture

#### Week 4 — Architecture (I) & Product Backlog

| Term | Definition | Source |
|---|---|---|
| [**software architecture**](chapters/week-04-architecture-i.html) | The **software architecture** of a program or computing system is the structure or structures of the system, which comprise software components, the externally visible properties of those components, and the relationships among them. Externally visible properties ≡ functionalities + NFR; in short, the architecture is the overall organization of the system — a high-level design. | Bass, Clements & Kazman, *Software Architecture in Practice* (2e), quoted on L4 slide 4 |
| [**component**](chapters/week-04-architecture-i.html) | A **component** is an element that models an application-specific function, responsibility, requirement, task, or process. | L4 slide 6 |
| [**connector**](chapters/week-04-architecture-i.html) | A **connector** is an element that models interactions among components for the purpose of transfer of control and/or data. | L4 slide 6 |
| [**architectural style**](chapters/week-04-architecture-i.html) | An **architectural style** is a named philosophy for organizing a system: it constrains how the code is divided (by technical concern or by business domain) and how the system is deployed (as a single deployed unit or as distributed units). | L4 slides 19–22 |
| [**Coupling**](chapters/week-04-architecture-i.html) | **Coupling** is the degree to which one module depends on other modules. The deck's types: content (a component modifies another's internal data), common/global (shared global variables), control (one module passes a flag dictating what another does), data (sharing data via parameters), external (dependencies outside the system, e.g., OS or hardware), temporal (bundled only because they occur at the same time), and inclusion/import. Lower coupling is better. | L4 slide 18, from Lethbridge & Laganière, ch. 9 |
| [**Cohesion**](chapters/week-04-architecture-i.html) | **Cohesion** is the degree to which the facilities within a module belong together. The deck's types: functional (one computation, no side effects), layer (related services together in a strict hierarchy), communicational (operating on the same data), sequential (output of one is input to the next), procedural (called one after another), temporal (same execution phase, e.g., initialization), and utility (grouped only because nothing stronger applies). Higher cohesion is better. | L4 slide 17, from Lethbridge & Laganière, ch. 9 |
| [**Modularity**](chapters/week-04-architecture-i.html) | **Modularity** is decomposing a big chunk into smaller chunks with well-defined interfaces (APIs) — a way to manage the complexity of a problem by breaking it into smaller manageable modules, allocating functions to modules and specifying APIs for their interactions. Modularization buys shorter development time, better flexibility, and better comprehensibility. | L4 slide 15, after David Parnas |
| [**modular monolith**](chapters/week-04-architecture-i.html) | A **modular monolith** is a system deployed as a single unit — a monolith — whose code is partitioned by business domain into modules with well-defined interfaces: domain partitioning combined with monolithic deployment. | L4 slide 22 (categorization summary |
| [**configuration**](chapters/week-04-architecture-i.html) | **The configuration** of an architecture is its topology or structure — the arrangement of the system's components and connectors. An architecture = components + connectors + configuration. | L4 slide 6 |
| [**reference architecture**](chapters/week-04-architecture-i.html) | A **reference architecture** explains the high-level structures of similar applications — numerous applications, same framework (e.g., web applications; the address-book developer guide's Logic/Storage/UI/Model organization) — and leads to architectural patterns. | L4 slide 9 |
| [**architectural pattern**](chapters/week-04-architecture-i.html) | An **architectural pattern** is an architectural solution that forms the basis for architectural design: it addresses an application-specific problem within a specific context, adhering to a set of limitations and constraints. | L4 slide 9 |
| [**Control flow**](chapters/week-04-architecture-i.html) | **Control flow** is the flow that reasons about computation order — how the focus of control moves throughout the execution; data may accompany control. | L4 slide 10 |
| [**Data flow**](chapters/week-04-architecture-i.html) | **Data flow** is the flow that reasons about data availability, transformation, and latency — how data moves through a collection of computations; as data moves, control is activated. | L4 slide 10 |
| [**Call and return**](chapters/week-04-architecture-i.html) | **Call and return** is the interaction style in which control moves from one component to another and back. It can be hierarchical (a master control calling subordinates) or non-hierarchical (objects calling each other's operations — e.g., through a manager for a shared abstract data type (ADT)). | L4 slide 11 |
| [**Horizontal slicing**](chapters/week-04-architecture-i.html) | **Horizontal slicing** cuts a system by technical layer: one slice is one layer — presentation, API, business logic, persistence — spanning every business domain; the boundary follows the technology. | L4 slide 16 |
| [**Vertical slicing**](chapters/week-04-architecture-i.html) | **Vertical slicing** cuts a system by business domain: one slice is one capability carried top to bottom — UI → endpoint → logic → persistence; the boundary follows the domain. | L4 slides 16, 20 |
| [**Functional cohesion**](chapters/week-04-architecture-i.html) | **Functional cohesion** is the strongest form of cohesion: the facilities in the module perform only one computation, with no side effects. | L4 slide 17, from Lethbridge & Laganière, ch. 9 |
| [**Layer cohesion**](chapters/week-04-architecture-i.html) | **Layer cohesion** keeps related services together and everything else out, in a strict hierarchy in which higher-level services can access only lower-level services; accessing a service may result in side effects. (As a cohesion type, "layer" describes the inside of one module — not the system-wide layers of the layered style.) | L4 slide 17, from Lethbridge & Laganière, ch. 9 |

| [**Model-View-Controller**](chapters/week-06-architecture-ii-and-rest.html) | **Model-View-Controller (MVC)** is an architectural style that separates an interactive application into three components: the **view** (the UI widgets the user sees), the **controller** (which coordinates between the model and the view, handling user input), and the **model** (which represents the business logic and holds the state of the system). | L6-Architecture slides 18–19 |

Owner services stream their data-change events into it via a messaging infrastructure, so cross-service queries never touch the services' own databases. %%(Source: L8 slide 11.)%% |  |
| [**Saga**](chapters/week-08-microservices-ii.html) | **Saga** — a sequence of local transactions in which each service performs its operation and initiates the next step through events or messages. Every step registers a compensating action (recorded on a *routing slip* — the coordination record that travels with the work and lists each remaining step and its undo) that is executed if a later step fails, bringing the system to a reasonably compensated state — not necessarily the original one. %%(Source: L8 slides 13–15.)%% |  |
| [**Event sourcing**](chapters/week-08-microservices-ii.html) | **Event sourcing** — a data storage pattern where state changes are stored as immutable events in an append-only log, and the current state is derived by applying the historical events, in sequence, to an initial state or snapshot. %%(Source: L8 slides 17–19.)%% %%(revisited as the storage view of an event in Week 9)%% |  |
| [**CQRS**](chapters/week-08-microservices-ii.html) | **CQRS** (command–query responsibility segregation) — a pattern that separates the write path (commands, which change application state and return no data) from the read path (queries, which return data and change nothing), giving each its own model and often its own database. CQRS does not require events or event sourcing; they are just mostly used together. %%(Source: L8 slides 22, 25–26; L9 slide 2.)%% %%(revisited in Week 9's four views of an event)%% |  |
| [**Materialized view**](chapters/week-08-microservices-ii.html) | **Materialized view** — a view (table) that contains the results of some predefined query, precomputed and stored. It is a performance optimization: instead of computing a query when a user needs data, the answer is stored and kept up to date. %%(Source: L8 slides 23–24.)%% |  |
| [**API gateway**](chapters/week-08-microservices-ii.html) | **API gateway** — a server that is the single entry point into a microservice system. It encapsulates the internal system architecture and provides an API tailored to each client, and may also handle authentication, monitoring, load balancing, and caching. %%(Source: L8 slide 31.)%% |  |
| [**Orchestration**](chapters/week-08-microservices-ii.html) | **Orchestration** — a way of coordinating a multi-service process that relies on a central "brain" to guide and drive the process, telling each participating service what to do next. %%(Source: L8 slide 32.)%% |  |
| [**Choreography**](chapters/week-08-microservices-ii.html) | **Choreography** — a way of coordinating a multi-service process that informs each part of the system of its job and lets it work out the details, typically by having each service react to events published by the others. %%(Source: L8 slide 32.)%% |  |
| [**Service registry**](chapters/week-08-microservices-ii.html) | **Service registry** — a database of available service instances and their locations. Service instances register on startup and deregister on shutdown; clients or routers query the registry to find an instance to call. %%(Source: L8 slides 34, 36.)%% |  |
| [**Atomicity**](chapters/week-08-microservices-ii.html) | **Atomicity** — the all-or-nothing property of a transaction: either every change in the group is applied or none is, so no observer sees a half-done operation (e.g., a paid booking must create the reservation *and* charge the card — both or neither). %%(Source: L8 slide 10 (the ACID properties); Quiz 3 Q2.)%% |  |
| [**Eventual consistency**](chapters/week-08-microservices-ii.html) | **Eventual consistency** — the consistency guarantee of a saga-coordinated design: temporary inconsistency between services is allowed while the business process runs, provided the system is guaranteed to reach a consistent state eventually, through completed steps or compensating actions. %%(Source: Tutorial 7 solutions Q1; L8 slides 13–15.)%% |  |
| [**Request/sync response**](chapters/week-08-microservices-ii.html) | **Request/sync response** — an interprocess communication style in which the client makes a request to a service and waits for the response before continuing (e.g., *Get passenger info*: TripManagement calls PassengerManagement and waits). %%(Source: L8 slide 30; Quiz 3 Q10.)%% |  |
| [**Notification**](chapters/week-08-microservices-ii.html) | **Notification (one-way request)** — an interprocess communication style in which the client sends a request and no reply is expected or sent (e.g., *Notify passenger*: DriverManagement tells PassengerManagement, and that is the whole conversation). %%(Source: L8 slide 30; Quiz 3 Q10.)%% |  |
| [**Request/async response**](chapters/week-08-microservices-ii.html) | **Request/async response** — an interprocess communication style in which the client sends a request and the service replies asynchronously, later (e.g., *Trip created*: TripManagement asks Dispatcher and the answer comes back when it is ready). %%(Source: L8 slide 30; Quiz 3 Q10.)%% |  |
| [**Client-side discovery**](chapters/week-08-microservices-ii.html) | **Client-side discovery** — a service-discovery style in which the client queries the service registry itself, determines the network locations of the available instances, and uses a load-balancing algorithm to pick one. %%(Source: L8 slide 34; Quiz 3 Q3.)%% |  |
| [**Server-side discovery**](chapters/week-08-microservices-ii.html) | **Server-side discovery** — a service-discovery style in which the client sends the request to a load balancer, which queries the service registry and routes each request to an available instance (e.g., NGINX Plus, AWS Elastic Load Balancer). %%(Source: L8 slide 35.)%% |  |

#### Week 9 — Event-Driven Architecture

| Term | Definition | Source |
|---|---|---|
| [**Event**](chapters/week-09-event-driven-architecture.html) | **Event** — a recording of something that has happened within the scope of the business system: a fact about a state change. Events act as both data and as a means of asynchronous communication between services. %%(Source: L9 slides 5–6.)%% |  |
| [**Initiating event**](chapters/week-09-event-driven-architecture.html) | **Initiating event** — an event that originates from an end user and typically kicks off a business process. %%(Source: L9 slide 7.)%% |  |
| [**Derived event**](chapters/week-09-event-driven-architecture.html) | **Derived event** — an internal event generated in response to an initiating event: a software component responds to the initiating event and in turn broadcasts what it did to the rest of the system, within the scope of that initiating event. %%(Source: L9 slide 8.)%% |  |
| [**Command**](chapters/week-09-event-driven-architecture.html) | **Command** — a request for an action to be performed, expressed as intent in the imperative mood (e.g., `ChargeCard`) and sent to a specific receiver; it changes application state and returns no data. %%(Source: L8 slides 4, 25; L9 slide 9.)%% |  |
| [**Query**](chapters/week-09-event-driven-architecture.html) | **Query** — a request that asks for the current state and needs a reply, but does not change state (e.g., `GetBalance`). %%(Source: L9 slide 9.)%% |  |
| [**Event notification**](chapters/week-09-event-driven-architecture.html) | **Event notification** — an event in its "something happened" role: it carries only a small amount of data, and consumers that need more must obtain it from the source. One of the four views of an event. %%(Source: L9 slide 5, from Fowler; Quiz 4 Q3.)%% |  |
| [**Event-carried state transfer**](chapters/week-09-event-driven-architecture.html) | **Event-carried state transfer** — an event in its "here is the data" role: the event carries the data consumers need, so they can work without calling the producer back. The other content-side view of an event. %%(Source: L9 slide 5, from Fowler.)%% |  |
| [**Fire-and-forget communication**](chapters/week-09-event-driven-architecture.html) | **Fire-and-forget communication** — asynchronous communication in which the sender broadcasts information and moves on: it does not wait for a response, nor does it care whether the other components are available. %%(Source: L9 slide 13.)%% |  |
| [**Event-driven architecture**](chapters/week-09-event-driven-architecture.html) | **Event-driven architecture (EDA)** — a software architectural design pattern in which decoupled applications (or components) asynchronously communicate by issuing and consuming events via an event broker; communication is through events, and events drive the system. %%(Source: L9 slides 20, 23.)%% |  |
| [**Event broker**](chapters/week-09-event-driven-architecture.html) | **Event broker** (aka event bus) — an intermediary that receives events from producers, holds them (in queues or partitions), and provides them to consumers that subscribe to topics of interest. It facilitates loose coupling: producers and consumers need not know each other's identity or location. %%(Source: L9 slides 21–23.)%% |  |
| [**Publish–subscribe**](chapters/week-09-event-driven-architecture.html) | **Publish–subscribe (pub/sub)** — a messaging pattern following the event-driven structure: event producers are publishers, event consumers are subscribers, and a broker delivers published events to every subscriber of the topic (e.g., Kafka pub/sub). %%(Source: L9 slide 24.)%% |  |
| [**Event stream**](chapters/week-09-event-driven-architecture.html) | **Event stream** — a partitioned, append-only sequence of related events published by one producing microservice, the owner of every event on that stream; consumers read it sequentially using offsets. %%(Source: L9 slides 32, 35–38.)%% |  |
| [**Event-driven microservice**](chapters/week-09-event-driven-architecture.html) | **Event-driven microservice** — a small application built to fulfill a specific bounded context that communicates by consuming events from one or more input event streams and producing events to other output event streams. %%(Source: L9 slides 32, 42.)%% |  |
| [**Temporal coupling**](chapters/week-09-event-driven-architecture.html) | **Temporal coupling** — the dependency between components that must be up at the same time for communication to work. Fire-and-forget communication removes it: producer and consumer do not need to be available simultaneously — the removal is often called temporal decoupling. %%(Source: L9 slide 17; Quiz 4 Q4.)%% |  |
| [**Latency**](chapters/week-09-event-driven-architecture.html) | **Latency** — the delay between sending a request and receiving (or completing) its response. Synchronous communication creates latency that slows the system, because the sender waits. %%(Source: L9 slide 25; Quiz 2 Q1; Quiz 3 Q10.)%% |  |
| [**Event key**](chapters/week-09-event-driven-architecture.html) | **Event key** — the key half of a key–value event: it identifies and routes the event, supports aggregation on the unique ID, and decides partition placement (all events produced with a given key are written to the same partition). By key, events come in three types: **unkeyed** (no key — a singular statement of fact), **entity** (keyed on the entity's unique ID — a continual history of that entity's state), and **keyed** (a key that does not represent an entity, used to guarantee data locality within a partition). %%(Source: L9 slide 10; L10 slide 23; Quiz 4 Q9.)%% |  |
| [**Immutability**](chapters/week-09-event-driven-architecture.html) | **Immutability (of event data)** — published events cannot be modified: there is no mechanism that can change event data once it is published; the only way to alter previous data is to publish a new event with the updated data. %%(Source: L9 slide 37; L8 slide 18.)%% |  |
| [**Offset**](chapters/week-09-event-driven-architecture.html) | **Offset** — the auto-incrementing index-ID of the last event a consumer has read in a partition. To consume, a service seeks to its offset, scans sequentially in publication order, and periodically records its new offset in the partition. %%(Source: L9 slides 35–37; Quiz 4 Q8–Q9.)%% |  |
| [**Partition**](chapters/week-09-event-driven-architecture.html) | **Partition** — one substream of an event stream: an append-only log into which the broker places events (by key). Data in a partition is strictly ordered and served in exactly the published order; partitions enable parallel reading and writing, and per-partition ordering says nothing about processing order across partitions. %%(Source: L9 slides 37–39; Quiz 4 Q8–Q9.)%% |  |
| [**Consumer group**](chapters/week-09-event-driven-architecture.html) | **Consumer group** — a set of load-balanced consumers that share the partitions of a stream between them, so the group's consumption capacity scales with its members; rate limits are applied to producers, consumers, and groups. %%(Source: L9 slides 39–40.)%% |  |
| [**Infinite retention**](chapters/week-09-event-driven-architecture.html) | **Infinite retention** — the broker property that an event stream retains its events for an infinite period of time, if so configured; it is foundational for maintaining state in an event stream. %%(Source: L9 slide 38; Quiz 4 Q4 (a seven-day retention window).)%% |  |
| [**Replayability**](chapters/week-09-event-driven-architecture.html) | **Replayability** — the broker property that any consumer can read whatever data it requires from the beginning of the stream; it provides the basis for the single source of truth and for communicating state between microservices. %%(Source: L9 slide 38.)%% |  |

#### Week 10 — Asynchronous Communication

| Term | Definition | Source |
|---|---|---|
| [**Synchronous communication**](chapters/week-10-asynchronous-communication.html) | **Synchronous communication** (request–reply) — components or services exchange information at the same time: the sender sends a request and waits for the receiver's response before doing anything else. It couples sender and receiver tightly, adds connection overhead, and leaves failure handling to the sender. %%(Source: L10 slide 5.)%% |  |
| [**Asynchronous communication**](chapters/week-10-asynchronous-communication.html) | **Asynchronous communication** — communication that has a lag between when a message is sent and when the receiver receives, interprets, or responds to it. It enables the independent functioning of sender and receiver and one-to-many sends, coupling them loosely — at the price of needing notification handling. %%(Source: L10 slide 5.)%% |  |
| [**Message**](chapters/week-10-asynchronous-communication.html) | **Message** — a construct carrying a *request to be executed* by another service: a command (perform some action) or a query (get some data), sent point-to-point to exactly one receiver. Intent — not wire format — is what distinguishes a message from an event. %%(Source: L10 slides 12–13.)%% |  |
| [**Topic**](chapters/week-10-asynchronous-communication.html) | **Topic** — a broker channel that enables one-to-many communication, reaching multiple subscribers simultaneously. Within a single partition, processing order is maintained through a unique offset per event; with multiple partitions, receive order may differ from send order. %%(Source: L10 slide 14.)%% |  |
| [**Queue**](chapters/week-10-asynchronous-communication.html) | **Queue** — a broker channel that buffers messages for a single receiver: it follows first-in-first-out, each message is consumed by exactly one receiver, and messages are not copied to other receivers. %%(Source: L10 slides 14, 24.)%% |  |
| [**Persistent communication**](chapters/week-10-asynchronous-communication.html) | **Persistent communication** (aka store-and-forward delivery) — messages are stored at each intermediate hop along the way until the next node is ready to take delivery; the message survives sender or receiver inactivity. E.g., email systems. %%(Source: L10 slide 32.)%% |  |
| [**Transient communication**](chapters/week-10-asynchronous-communication.html) | **Transient communication** — messages are buffered only for small periods of time (as long as the sending/receiving applications are executing); if the message cannot be delivered or the next host is down, it is discarded. Sender and receiver must both be active. E.g., a typical network router (general TCP/IP communication). %%(Source: L10 slide 32.)%% |  |
| [**Asynchronous request–reply**](chapters/week-10-asynchronous-communication.html) | **Asynchronous request–reply** — a pattern for long-running work kept behind a request–reply facade: the API accepts the request, queues it for a background worker, and answers immediately with **HTTP 202 (Accepted)** plus a link to a *status endpoint*; the client polls the status endpoint (202 while pending), and on completion receives **302 (Found)** redirecting to the resource. An invalid request is rejected immediately (e.g. HTTP 400 Bad Request). %%(Source: L10 slides 7–8; Quiz 4 Q7.)%% |  |
| [**Kafka**](chapters/week-10-asynchronous-communication.html) | **Kafka** — a distributed message streaming platform that uses publish–subscribe, developed at LinkedIn and donated to the Apache Foundation: producers publish events to named topics, topics are broken into partitions spread over a cluster of brokers that deliver messages to consumers, and brokers can be added without downtime — horizontal scaling. %%(Source: L10 slides 22–23.)%% |  |
| [**AMQP**](chapters/week-10-asynchronous-communication.html) | **AMQP** (Advanced Message Queuing Protocol) — an open-standard asynchronous messaging protocol enabling conforming client applications to communicate with conforming messaging middleware brokers: messages are published to exchanges, which route copies to queues, from which consumers receive or fetch them. %%(Source: L10 slides 25–27.)%% |  |
| [**Exchange**](chapters/week-10-asynchronous-communication.html) | **Exchange** (AMQP/RabbitMQ) — the routing step of the AMQP model: it receives published messages and routes copies into the queues bound to it, matching message attributes (e.g., the routing key) against each queue's binding. Exchange types: **direct** (exact key match), **fanout** (all bound queues), **topic** (wildcard match, e.g. `us.#` matches `us.stocks`), **header** (route on message headers). %%(Source: L10 slides 26, 28–29.)%% |  |
| [**Protocol**](chapters/week-10-asynchronous-communication.html) | **Protocol** — a set of rules for communication (e.g., AMQP). A **standard** is a protocol approved by an authority (the slide names IEEE, W3C) and adopted by many parties — protocols can also be non-standard (e.g., JMS). A **specification** is the formally written form of a protocol that vendors follow (Java provides the JMS specification). An **implementation** is a vendor's working mechanism for using the protocol (e.g., ActiveMQ, Kafka). %%(Source: L10 slide 10.)%% |  |

#### Week 11 — Messaging

| Term | Definition | Source |
|---|---|---|
| [**Message construction**](chapters/week-11-messaging.html) | **Message construction** is the choice of what a message should contain and what the receiver should do with it. The three payload kinds are the **command message** (tells the receiver to do something), the **document message** (gives the receiver data to process) and the **event message** (notifies the receiver that something has happened). | L11 slides 16–18; Enterprise Integration Patterns, eaipatterns.com |
| [**Pipes and filters**](chapters/week-11-messaging.html) | **Pipes and filters** is a message-flow pattern that connects single-purpose processing steps (*filters*) with message channels (*pipes*): each filter consumes a message, performs one transformation or routing decision, and passes the result to the next filter. A splitter feeding a content-based router feeding an aggregator is a pipes-and-filters flow. | L11 slides 15, 46–51; Enterprise Integration Patterns, eaipatterns.com |
| [**Content filter**](chapters/week-11-messaging.html) | **Content filter** is a message-transformation pattern that removes data items the receiver does not need from a message before passing it on, so that each message carries only what its consumer requires. | L11 slide 15 (pattern map); Enterprise Integration Patterns, eaipatterns.com |
| [**Content enricher**](chapters/week-11-messaging.html) | **Content enricher** is a message-transformation pattern that adds data items a message needs but does not carry, typically by looking them up from another source, before passing the message on. | L11 slide 15 (pattern map); Enterprise Integration Patterns, eaipatterns.com |
| [**Message router**](chapters/week-11-messaging.html) | **Message router** — a component that consumes messages from one message channel and reinserts them into different message channels depending on a set of conditions, encapsulating the routing logic so the sender's workload is reduced. Simple routers connect one inbound channel to one or more outbound channels; composed routers combine several simple routers into more complex flows. | L11 slides 34–35 |
| [**Content-based router**](chapters/week-11-messaging.html) | **Content-based router** — a router that examines the message content and routes each message onto a channel chosen from the data contained in it, decoupling sender from receiver. It must know all possible recipients and their capabilities, so a change in the recipient list means a change in the router. | L11 slide 36 |
| [**Message filter**](chapters/week-11-messaging.html) | **Message filter** — a content-based router with a single output channel: messages whose content matches the filter's criteria are routed on; the rest are discarded. | L11 slide 37 |
| [**Context-based router**](chapters/week-11-messaging.html) | **Context-based router** — a router that decides the message's destination from the *context* rather than the message content — commonly for load balancing, testing, or failover (e.g., re-routing messages to another processing component when one fails). | L11 slide 40 |
| [**Splitter**](chapters/week-11-messaging.html) | **Splitter** — a message-flow pattern that turns a single message into multiple messages, one per part (e.g., one order message with N items becomes N order-item messages, each routable separately); it is not a router itself. | L11 slide 47 |
| [**Aggregator**](chapters/week-11-messaging.html) | **Aggregator** — a stateful filter that receives a stream of messages, identifies the correlated ones (e.g., by order ID), and — once a complete set of correlated messages has arrived — collects the information from each and publishes a single aggregated message to the output channel. | L11 slide 48 |
| [**Scatter-gather**](chapters/week-11-messaging.html) | **Scatter-gather** — a routing pattern that broadcasts one message to a number of participants concurrently and reassembles (aggregates) their replies into a single message; ideal for requesting responses from multiple parties, e.g. quotes from all suppliers of an out-of-stock item. | L11 slide 52 |
| [**Message translator**](chapters/week-11-messaging.html) | **Message translator** — a component that encapsulates the conversion of messages between two data formats, sitting between client and service so neither side has to change. | L11 slides 55–56 |
| [**Channel adapter**](chapters/week-11-messaging.html) | **Channel adapter** — a pattern that converts between different transport layers: an adapter converts the interface of a component into another interface so it can be used in a different context (e.g., the transport-layer adapter beside an EDI-to-XML translator). | L11 slide 56 |
| [**Canonical data model**](chapters/week-11-messaging.html) | **Canonical data model** — a common intermediate format that provides an additional level of indirection between applications' individual data formats: each system translates its data into the canonical syntax when sending and out of it when receiving, replacing the unmanageable one-translator-per-pair explosion with one adapter per system. | L11 slides 57–58 |
| [**Message endpoint**](chapters/week-11-messaging.html) | **Message endpoint** — the interface between an application and a messaging system: it encapsulates the messaging APIs (e.g., JMS) and is custom to both the application and the messaging system's client API, so the rest of the application knows little about message formats, channels, or other messaging details. Endpoints are channel-specific and one-directional — one instance either sends or receives, not both. | L11 slides 60–61 |
| [**Polling consumer**](chapters/week-11-messaging.html) | **Polling consumer** — a receiving endpoint that proactively reads messages when *it* is ready to consume them (e.g., RabbitMQ's `basic.get`). | L11 slides 61–62 |
| [**Event-driven consumer**](chapters/week-11-messaging.html) | **Event-driven consumer** — a receiving endpoint that reacts to a message's arrival, processing it as an event that triggers the receiver into action (e.g., RabbitMQ's `basic.consume`). | L11 slide 63 |
| [**Throttling**](chapters/week-11-messaging.html) | **Throttling** — a receiver-side control on the rate at which an application consumes messages, so consumption matches the application's current capacity. | L11 slide 61 |
| [**Pseudo-asynchronous**](chapters/week-11-messaging.html) | **Pseudo-asynchronous** — an interaction that returns control to the caller immediately but is still synchronous in terms of *dependency*: the caller cannot complete its overall operation until the reply arrives (e.g., Module A returning at once while a background process waits on B's HTTP response it still needs). Judge asynchronicity by dependency, not by technology. | L11 slides 3, 20–25; Tutorial 8 Q1 |
| [**Request-reply**](chapters/week-11-messaging.html) | **Request-reply** is an asynchronous messaging pattern in which a requestor sends a request message on one channel — carrying a *return address* saying where the reply should go — and later matches the reply message to the request using a *correlation identifier*, instead of blocking on a synchronous call. | L11 slides 20–25; Enterprise Integration Patterns, eaipatterns.com |
| [**Enterprise Integration Patterns**](chapters/week-11-messaging.html) | **Enterprise Integration Patterns (EIP)** — a technology-independent catalogue of 65 solutions to common integration problems (Hohpe & Woolf), organised in six categories: message construction, message channels, message routing, message transformation, message endpoints, and system management. EIP give developers and architects a shared, vendor-independent vocabulary for describing integrations. | L11 slides 8, 14–15; Enterprise Integration Patterns, eaipatterns.com |
| [**Message broker**](chapters/week-11-messaging.html) | **Message broker** (aka MOM — message-oriented middleware) — software that provides messaging capabilities so applications can exchange messages without knowing each other's location, platform, or implementation: it passes information between components while minimising how much they need to know about each other, buffers incoming messages, and shields applications from many operating-system and network complexities. | L11 slides 11, 64 |
| [**Command message**](chapters/week-11-messaging.html) | **Command message** — a message whose payload tells the receiver to perform some action (e.g., `ReserveEquipment` to the Reservation service); a reply is typically expected (request-reply). | L11 slides 16–18; Quiz 4 Q1 |
| [**Document message**](chapters/week-11-messaging.html) | **Document message** — a message whose payload gives the receiver data to process at its own discretion; no reply is expected (e.g., the purchase-order document translated to XML for the order-management system). | L11 slides 16–18, 56 |
| [**Event message**](chapters/week-11-messaging.html) | **Event message** — a message whose payload notifies the receiver that something has happened — a completed fact the receiver may react to (e.g., `EquipmentReserved`, published only after a reservation succeeds). | L11 slides 16–18; Quiz 4 Q1 |
| [**Message channel**](chapters/week-11-messaging.html) | **Message channel** — the conduit that connects collaborating senders and receivers and carries messages between them: a queue (point-to-point — exactly one consumer per message) or a topic (publish–subscribe — all subscribers). A channel transmits messages in one direction, so a two-way exchange needs two channels. | L11 slides 19–20, 31–32 |
| [**Point-to-point channel**](chapters/week-11-messaging.html) | **Point-to-point channel** — a channel (a queue) on which exactly one consumer consumes each message, even if several consumers listen on it — the shape that lets competing consumers share the load. | L11 slides 20, 24, 31–32 |
| [**Publish–subscribe channel**](chapters/week-11-messaging.html) | **Publish–subscribe channel** — a channel (a topic) on which any message published is immediately received by all subscribers of the topic; used when multiple parties are interested in the same messages. A pub-sub *request–response* variant uses a pub-sub channel for the requests but a point-to-point channel for the responses. | L11 slides 31–32 |
| [**Return address**](chapters/week-11-messaging.html) | **Return address** — the part of a request message that tells the replier where to send the reply (e.g., the request's `Reply to: jms/ReplyQueue` field). | L11 slides 22–23 |
| [**Correlation identifier**](chapters/week-11-messaging.html) | **Correlation identifier** — a token the requestor assigns as a unique request ID (different from all currently outstanding requests) and the replier copies into the reply, so the requestor can match each reply to the request that caused it. | L11 slides 24–25; Quiz 4 Q7 |
| [**Request-reply chaining**](chapters/week-11-messaging.html) | **Request-reply chaining** — keeping the correlation of a chain of request-reply exchanges (a request causes a reply that is itself another request, and so on), so the path of messages can be retraced from the latest reply back to the original request — e.g., for auditing. | L11 slide 26 |
| [**Invalid message channel**](chapters/week-11-messaging.html) | **Invalid message channel** — a channel that receives messages a receiver cannot interpret, so erroneous messages are moved aside instead of blocking or crashing the receiver. | L11 slide 27 |
| [**Dead letter channel**](chapters/week-11-messaging.html) | **Dead letter channel** (dead-letter queue, DLQ) — a channel that receives messages the messaging system cannot deliver or that repeatedly fail processing: instead of retrying failing messages until they expire, move them to the dead-letter queue after a few processing attempts. | L11 slide 27; Tutorial 9 Q4 |
| [**Redrive**](chapters/week-11-messaging.html) | **Redrive** — moving messages from a dead-letter queue back to the source queue (or to another configured queue) for another processing attempt, once the cause of the failures has been found and fixed. (AWS SQS's term for managing the lifecycle of unconsumed messages.) | L11 slide 28; Tutorial 9 Q4 |
| [**Data type channel**](chapters/week-11-messaging.html) | **Data type channel** — one channel per data type: all messages on a given channel contain the same type of data, so the receiver knows the type from the channel a message arrived on; the sender, knowing the type, selects the appropriate channel. | L11 slide 29 |

#### Week 12 — Scalability

| Term | Definition | Source |
|---|---|---|
| [**Scalability**](chapters/week-12-scalability.html) | **Scalability** is the property of a system to handle a growing amount of work by adding resources to the system. The growth may be in requests processed per time window or in the amount of data managed, while response times stay stable and consistent. | L12 slides 4–6; recap of L3, slide 3 |
| [**Vertical scaling**](chapters/week-12-scalability.html) | **Vertical scaling (scale up)** adds capability to the machines a system is deployed on — e.g. more CPU or memory on the same node — without adding more nodes. It is simple but capped by the hardware limits of a single machine. | L12 slides 3, 11 |
| [**Horizontal scaling**](chapters/week-12-scalability.html) | **Horizontal scaling (scale out)** adds additional machines (nodes) running copies of the service, so that requests are distributed across the replicas. With N replicas and R requests, each server processes about R/N requests. | L12 slides 3, 12 |
| [**Load balancing**](chapters/week-12-scalability.html) | **Load balancing** sends all user requests to a component that chooses which service replica will process each request — aiming to keep every replica equally busy — and relays the responses back to the clients. | L12 slide 13 |
| [**Stateless service**](chapters/week-12-scalability.html) | **Stateless service** is a service whose API implementation retains no state associated with an individual client's session, so any replica can process any request. Session state is kept in a shared session store that every replica can access, which is what makes stateless services cheap to replicate. | L12 slide 14 |
| [**Autoscaling**](chapters/week-12-scalability.html) | **Autoscaling** — automatically growing or shrinking a system's capacity on a metric (e.g., CPU usage, queue length) so capacity follows the load up *and* down — load is not constant (a streaming service at 9 pm faces far more load than at 5 am). | L12 slide 6 |
| [**Percentile**](chapters/week-12-scalability.html) | **Percentile** (P50/P95/P99) — a point on the response-time distribution: P50 (the median) is a typical user's experience; P95 means 95% of requests are faster than this number — a standard threshold for service-level objectives; P99 captures the worst-case scenarios. Response time is a distribution, not a number. | L12 slide 7 |
| [**Service-level objective**](chapters/week-12-scalability.html) | **Service-level objective (SLO)** — a measurable target for a service level that a team commits to, typically written on percentile response times held over a window — e.g., 95% of successful browse errand requests complete in under 200 ms in a 7-day window. | L12 slide 7 |
| [**Tail latency**](chapters/week-12-scalability.html) | **Tail latency** — the response times of the slowest few percent of requests, beyond the P95/P99 thresholds. The users at the tail are the ones who notice, which is why service-level objectives are written on tail percentiles rather than on the average. | L12 slide 7 |
| [**Bottleneck**](chapters/week-12-scalability.html) | **Bottleneck** — the slowest shared component that limits the whole system's response time or throughput (e.g., the single overloaded server, the one database every replica shares). Measure first, then plan the scaling strategy — scaling the wrong component buys nothing. | L12 slides 7, 10, 15; Quiz 3 Q1 |
| [**Replicating resources**](chapters/week-12-scalability.html) | **Replicating resources** — the scaling strategy of adding copies of what you have to provide more capacity to handle requests, increasing throughput. One of the two levers; the other is optimizing the available resources. | L12 slide 8 |
| [**Optimizing the available resources**](chapters/week-12-scalability.html) | **Optimizing the available resources** — the scaling strategy of getting more out of the same hardware: more efficient algorithms, extra indices to speed up queries, rewriting a server in a faster programming language (e.g., Facebook developed HipHop, a compiler for PHP). | L12 slide 8 |
| [**Throughput**](chapters/week-12-scalability.html) | **Throughput** — the amount of work a system processes per unit time (e.g., requests per second); replicating resources to add capacity increases it. | L12 slide 8 |
| [**Single point of failure**](chapters/week-12-scalability.html) | **Single point of failure** — a component whose failure takes the whole system down because no replica can take over (e.g., the single machine of scale-up, the single primary database). Horizontal scaling and read replicas exist to remove it. | L12 slides 11, 17 |
| [**Session store**](chapters/week-12-scalability.html) | **Session store** — shared storage holding users' session state, accessible from every service replica. Because the load balancer sends consecutive requests from the same client to different instances, session state must live here rather than inside any replica. | L12 slide 14 |
| [**Read replica**](chapters/week-12-scalability.html) | **Read replica** — a secondary database node that receives changes from the primary by asynchronous replication and serves reads (possibly from other regions, to support global clients). Writes go only to the primary, so replicas add read capacity and locality — not write capacity. | L12 slide 17 |
| [**Partitioning**](chapters/week-12-scalability.html) | **Partitioning** (sharding) — splitting one logical table across several physical stores: horizontal partitioning allocates rows to partitions by a partitioning strategy (e.g., value-based, a hash of the primary key); vertical partitioning partitions by columns (e.g., static read-only data apart from dynamic data). Each partition — shard — runs the same code on a subset of the data. | L12 slides 18, 24 |
| [**Distributed database**](chapters/week-12-scalability.html) | **Distributed database** — a database scaled by adding storage nodes: data is stored across multiple disks and queried by multiple database engines that put up a logical unified front to the application; it also improves availability. | L12 slides 19–20 |
| [**Backend-for-frontend**](chapters/week-12-scalability.html) | **Backend-for-frontend (BFF)** — a multi-tier scaling variant in which each frontend gets its own purpose-built backend tier (the web tier serving web clients, the mobile tier serving mobile clients), shaped for that client's needs and scaled on that client's load; all tiers use a core service that provides database access. | L12 slide 21 |
| [**Swim lane**](chapters/week-12-scalability.html) | **Swim lane** (pod) — a boundary placing a group of services so that any failure within the boundary is contained and not propagated outside it. Advantages: easy fault detection within the lane, fault isolation, meeting region-specific requirements, faster customer-specific response. (The scalability literature's term — not a Kubernetes pod.) | L12 slide 23 |
| [**Scale cube**](chapters/week-12-scalability.html) | **Scale cube** — the three-axis summary of scaling strategies: **X-axis** — horizontal scaling, running multiple copies of the application behind a load balancer; **Y-axis** — functional decomposition, splitting the application into multiple different functions/services; **Z-axis** — running the same code on a subset of the data (data partitioning, e.g., segmented by customer category or geography). The axes compose. | L12 slide 24 |
