#### Week 2 — Modern Software Engineering

| Term | Definition | Source |
|---|---|---|
| [**CI/CD**](chapters/week-02-modern-software-engineering.html) | **CI/CD** is the pairing of two delivery practices: **continuous integration (CI)** — developers integrate code into a shared repository several times a day, each check-in verified by an automated build so problems are detected early — and **continuous delivery/deployment (CD)** — every good build is kept potentially ready for production release (delivery), or released automatically into production (deployment). | L1 slides 41–42 |
| [**DevOps**](chapters/week-02-modern-software-engineering.html) | **DevOps** is a set of software development practices that combines software development (Dev) and operations (Ops), intending to reduce the time between committing a change and that change running in normal production, while ensuring high quality. | L1 slide 46, after Ebert et al., IEEE Software 2016 |
| [**Containerization**](chapters/week-02-modern-software-engineering.html) | **Containerization** is packaging an application together with only the OS processes and dependencies it needs, so it runs identically on any host that runs a container engine — lighter than a virtual machine, which carries a full guest OS. | L1 slides 32–33 |
| [**Blue-green deployment**](chapters/week-02-modern-software-engineering.html) | **Blue-green deployment** is a release strategy that shifts traffic between two identical environments running different versions of the application, achieving near-zero downtime and easy rollback. | L1 slide 44 |
| [**Vibe coding**](chapters/week-02-modern-software-engineering.html) | **Vibe coding** is building software primarily by prompting AI — compressing the distance from idea to prototype, requirement to interface, and prompt to implementation — while accepting weaker architecture, quality, and a larger verification burden. | L2 slide 11 |

#### Week 3 — Requirements

| Term | Definition | Source |
|---|---|---|
| [**requirement**](chapters/week-03-requirements.html) | A **requirement** is a condition or capability needed by a user to solve a problem or achieve an objective, or a condition or capability that must be met or possessed by a system to satisfy a contract, standard, specification, or other formally imposed document — or a documented representation of either. | IEEE, quoted on L3 slide 3 |
| [**functional requirement**](chapters/week-03-requirements.html) | A **functional requirement (FR)** specifies something the system should do — typically a behavior or function, e.g., "The passenger shall be able to print boarding passes for all flight segments for which she has checked in." | L3 slide 9 |
| [**non-functional requirement**](chapters/week-03-requirements.html) | A **non-functional requirement (NFR)** describes a constraint on the system or its development that is not directly related to specific functionality — it describes how well the system works, e.g., "Mean time between failure ≥ 9000 hrs." | L3 slide 9 |
| [**quality attribute**](chapters/week-03-requirements.html) | A **quality attribute** is a property of the system — such as performance, scalability, security, or usability — that contributes to its quality; a combination of quality attributes defines the software quality, and they are usually stated as non-functional requirements. | L3 slide 10 |
| [**requirement trade-off**](chapters/week-03-requirements.html) | A **requirement trade-off** is a design situation in which improving one quality attribute degrades another — e.g., adding redundant checks and backups improves reliability but makes the system slower and costlier — forcing prioritization under resource constraints. | L3 slide 23 |
| [**product backlog**](chapters/week-03-requirements.html) | A **product backlog** is the ordered list of a product's requirements, each with a type, a unique identifier, a description, a priority, and a planned sprint; it allows work allocation, developing test specifications, and design development. | L3 slides 7, 26 |

### Architecture

#### Week 4 — Architecture (I) & Product Backlog

| Term | Definition | Source |
|---|---|---|
| [**software architecture**](chapters/week-04-architecture-i.html) | The **software architecture** of a program or computing system is the structure or structures of the system, which comprise software components, the externally visible properties of those components, and the relationships among them. Externally visible properties ≡ functionalities + NFR; in short, the architecture is the overall organization of the system — a high-level design. | Bass, Clements & Kazman, *Software Architecture in Practice* (2e), quoted on L4 slide 4 |
| [**component**](chapters/week-04-architecture-i.html) | A **component** is an element that models an application-specific function, responsibility, requirement, task, or process. | L4 slide 6 |
| [**connector**](chapters/week-04-architecture-i.html) | A **connector** is an element that models interactions among components for the purpose of transfer of control and/or data. | L4 slide 6 |
| [**architectural style**](chapters/week-04-architecture-i.html) | An **architectural style** is a named philosophy for organizing a system: it constrains how the code is divided (by technical concern or by business domain) and how the system is deployed (as a single deployed unit or as distributed units). | L4 slides 19–22 |
| [**Coupling**](chapters/week-04-architecture-i.html) | **Coupling** is the degree to which one module depends on other modules. The deck's types: content (a component modifies another's internal data), common/global (shared global variables), control (one module passes a flag dictating what another does), data (sharing data via parameters), external (dependencies outside the system, e.g., OS or hardware), temporal (bundled only because they occur at the same time), and inclusion/import. Lower coupling is better. | L4 slide 18, from Lethbridge & Laganière, ch. 9 |
| [**Cohesion**](chapters/week-04-architecture-i.html) | **Cohesion** is the degree to which the facilities within a module belong together. The deck's types: functional (one computation, no side effects), layer (related services together in a strict hierarchy), communicational (operating on the same data), sequential (output of one is input to the next), procedural (called one after another), temporal (same execution phase, e.g., initialization), and utility (grouped only because nothing stronger applies). Higher cohesion is better. | L4 slide 17, from Lethbridge & Laganière, ch. 9 |
| [**Modularity**](chapters/week-04-architecture-i.html) | **Modularity** is decomposing a big chunk into smaller chunks with well-defined interfaces (APIs) — a way to manage the complexity of a problem by breaking it into smaller manageable modules, allocating functions to modules and specifying APIs for their interactions. Modularization buys shorter development time, better flexibility, and better comprehensibility. | L4 slide 15, after David Parnas |
| [**modular monolith**](chapters/week-04-architecture-i.html) | A **modular monolith** is a system deployed as a single unit — a monolith — whose code is partitioned by business domain into modules with well-defined interfaces: domain partitioning combined with monolithic deployment. | L4 slide 22 (categorization summary |

#### Week 6 — Architecture (II) & REST

| Term | Definition | Source |
|---|---|---|
| [**Model-View-Controller**](chapters/week-06-architecture-ii-and-rest.html) | **Model-View-Controller (MVC)** is an architectural style that separates an interactive application into three components: the **view** (the UI widgets the user sees), the **controller** (which coordinates between the model and the view, handling user input), and the **model** (which represents the business logic and holds the state of the system). | L6-Architecture slides 18–19 |
| [**single-page application**](chapters/week-06-architecture-ii-and-rest.html) | **A single-page application (SPA)** is a (JavaScript) program downloaded into the browser that runs continuously there, sending queries and retrieving data in the background without refreshing the web page. | L6-Architecture slides 23–25 |
| [**REST**](chapters/week-06-architecture-ii-and-rest.html) | **REST (REpresentational State Transfer)** is an architectural style for distributed hypermedia systems, defined by a set of constraints — client-server, stateless, cacheable, layered system, uniform interface, and optionally code-on-demand — for transferring, accessing, and manipulating textual representations of resources in a stateless manner across a network. | L6-REST slides 3–6 |
| [**Statelessness**](chapters/week-06-architecture-ii-and-rest.html) | **Statelessness** is the REST constraint that each client-server interaction must be entirely self-contained: the full information needed to serve a request travels in the request itself (URI, headers, query parameters), and the server maintains no client session state. | L6-REST slide 8 |
| [**uniform interface**](chapters/week-06-architecture-ii-and-rest.html) | **The uniform interface** is the REST constraint that there be one standard way of interacting with a server, irrespective of the client's device or application type: requests use the HTTP verbs (GET, PUT, POST, DELETE), responses use HTTP status codes, and the resource representation travels in the HTTP body. | L6-REST slides 11–12 |
| [**layered architectural style**](chapters/week-06-architecture-ii-and-rest.html) | **The layered architectural style** organizes software as layers of components whose dependencies all point downward: each layer has a distinct and specific responsibility, and a layer obtains services from the layer(s) below it. | L6-Architecture slides 6–8 |
| [**pipe-and-filter architectural style**](chapters/week-06-architecture-ii-and-rest.html) | **The pipe-and-filter architectural style** divides an application's task into a sequence of self-contained processing steps (**filters**) connected by intermediate data channels (**pipes**): each filter transforms its input stream, computes incrementally, produces output in a defined format, and shares no state with the other filters. | L6-Architecture slides 9–12 |

### Distributed Systems & Microservices

#### Week 7 — Microservices (I)

| Term | Definition | Source |
|---|---|---|
| [**microservice**](chapters/week-07-microservices-i.html) | **A microservice** is an independently deployable service modeled around a business domain: it offers a well-defined business capability, is small and lightweight, is owned by a small team, and communicates with other services through well-defined, published interfaces. | L7 slides 5–7 (first introduced in L5 slide 21, guest lecture by Dell |
| [**Microservice architecture**](chapters/week-07-microservices-i.html) | **Microservice architecture** is an architectural style that structures an application as a collection of services that are organized around business capabilities, loosely coupled, owned by small teams, and independently deployable — a suite of small services that work with each other to form a bigger solution. | L7 slides 5–7 |
| [**Loose coupling**](chapters/week-07-microservices-i.html) | **Loose coupling** is the design property in which components depend on each other only through small, published interfaces and share no internals — no shared code, databases, or implementation knowledge — so each component can change, deploy, and fail without forcing changes on the others. | L7 slides 7 and 10; L5 slides 23–24 (guest lecture by Dell |
| [**Domain-driven design**](chapters/week-07-microservices-i.html) | **Domain-driven design (DDD)** is a domain-centric approach to software design for complex problem domains: a collection of patterns, principles, and practices that keeps the domain model isolated from technical complexities so that the software closely reflects business needs. | L7 slide 20 |
| [**domain model**](chapters/week-07-microservices-i.html) | **A domain model** is an abstraction of the problem domain — a view of the domain containing only the information necessary to solve the problem in the context of the application. It is not the reality; deciding what to retain and what to ignore is the modeling act. | L7 slides 17–18 |
| [**sub-domain**](chapters/week-07-microservices-i.html) | **A sub-domain** is a logical separation of the domain: a cohesive unit of business functionality focused on a specific set of responsibilities, typically reflecting part of the business organization's structure. Sub-domains are classified as **core** (the key differentiator — build in-house), **supporting** (related but not a differentiator — build or outsource), or **generic** (not specific to the business — buy off-the-shelf). %%(revisited with the FoC example in Week 8)%% | L7 slides 18–19 |
| [**bounded context**](chapters/week-07-microservices-i.html) | **A bounded context** is an explicit boundary within which a domain model exists: a highly cohesive boundary including the input, output, events, requirements, processes, and data models relevant to a sub-domain. Bounded contexts belong to the solution space and ideally align with sub-domains of the problem space. %%(revisited with the FoC example in Week 8)%% | L7 slides 21 and 32 |
| [**ubiquitous language**](chapters/week-07-microservices-i.html) | **A ubiquitous language** is a shared language between domain experts and developers, built from business terms and used in conversations, requirements, design, and code — scoped to a bounded context, with one meaning per term inside that context. The same word can mean something else in another context. %%(revisited with the FoC example in Week 8)%% | L7 slides 22–23 |
| [**aggregate**](chapters/week-07-microservices-i.html) | **An aggregate** is a cluster of related objects treated as a single unit for the purpose of data changes. It has a **root** — the parent entity that forms the aggregate's public interface — and **boundaries**: a consistency boundary (everything outside may only read the aggregate's state; state changes only through the public interface) and a transactional boundary (any change either all succeeds or none succeeds). | L7 slide 33 |

#### Week 8 — Microservices (II) & DDD

| Term | Definition | Source |
|---|---|---|
| [**Domain**](chapters/week-08-microservices-ii.html) | **Domain** — the problem space that a business occupies and provides a solution for. E.g., the FoC platform's domain is peer-to-peer campus errands. %%(Source: L8 slides 2–3.)%% |  |
| [**Event storming**](chapters/week-08-microservices-ii.html) | **Event storming** — a lightweight workshop practice for discovering microservices: identify the domain events that record state changes, then the commands that cause them, the aggregates the commands work on, and the policies that react to events. %%(Source: L8 slides 2, 4.)%% |  |
| [**Database-server-per-service pattern**](chapters/week-08-microservices-ii.html) | **Database-server-per-service pattern** — each microservice has its own database server that no other service touches directly. It enforces loose coupling, allows scaling at the database level, and lets each service choose or replace its database technology freely. %%(Source: L8 slides 6, 8.)%% |  |
| [**Shared database pattern**](chapters/week-08-microservices-ii.html) | **Shared database pattern** — multiple services read and write one common database. It is an antipattern for microservices: it creates development-time coupling (schema changes need team coordination), runtime interference (services overwrite each other's data), and forces one database technology on all services. %%(Source: L8 slide 10.)%% |  |
| [**Data lake**](chapters/week-08-microservices-ii.html) | **Data lake** — a read-only, queryable data sink holding (copies of) data from several microservices, indexed for queryability. Owner services stream their data-change events into it via a messaging infrastructure, so cross-service queries never touch the services' own databases. %%(Source: L8 slide 11.)%% |  |
| [**Saga**](chapters/week-08-microservices-ii.html) | **Saga** — a sequence of local transactions in which each service performs its operation and initiates the next step through events or messages. Every step registers a compensating action (recorded on a *routing slip* — the coordination record that travels with the work and lists each remaining step and its undo) that is executed if a later step fails, bringing the system to a reasonably compensated state — not necessarily the original one. %%(Source: L8 slides 13–15.)%% |  |
| [**Event sourcing**](chapters/week-08-microservices-ii.html) | **Event sourcing** — a data storage pattern where state changes are stored as immutable events in an append-only log, and the current state is derived by applying the historical events, in sequence, to an initial state or snapshot. %%(Source: L8 slides 17–19.)%% %%(revisited as the storage view of an event in Week 9)%% |  |
| [**CQRS**](chapters/week-08-microservices-ii.html) | **CQRS** (command–query responsibility segregation) — a pattern that separates the write path (commands, which change application state and return no data) from the read path (queries, which return data and change nothing), giving each its own model and often its own database. CQRS does not require events or event sourcing; they are just mostly used together. %%(Source: L8 slides 22, 25–26; L9 slide 2.)%% %%(revisited in Week 9's four views of an event)%% |  |
| [**Materialized view**](chapters/week-08-microservices-ii.html) | **Materialized view** — a view (table) that contains the results of some predefined query, precomputed and stored. It is a performance optimization: instead of computing a query when a user needs data, the answer is stored and kept up to date. %%(Source: L8 slides 23–24.)%% |  |
| [**API gateway**](chapters/week-08-microservices-ii.html) | **API gateway** — a server that is the single entry point into a microservice system. It encapsulates the internal system architecture and provides an API tailored to each client, and may also handle authentication, monitoring, load balancing, and caching. %%(Source: L8 slide 31.)%% |  |
| [**Orchestration**](chapters/week-08-microservices-ii.html) | **Orchestration** — a way of coordinating a multi-service process that relies on a central "brain" to guide and drive the process, telling each participating service what to do next. %%(Source: L8 slide 32.)%% |  |
| [**Choreography**](chapters/week-08-microservices-ii.html) | **Choreography** — a way of coordinating a multi-service process that informs each part of the system of its job and lets it work out the details, typically by having each service react to events published by the others. %%(Source: L8 slide 32.)%% |  |
| [**Service registry**](chapters/week-08-microservices-ii.html) | **Service registry** — a database of available service instances and their locations. Service instances register on startup and deregister on shutdown; clients or routers query the registry to find an instance to call. %%(Source: L8 slides 34, 36.)%% |  |

#### Week 9 — Event-Driven Architecture

| Term | Definition | Source |
|---|---|---|
| [**Event**](chapters/week-09-event-driven-architecture.html) | **Event** — a recording of something that has happened within the scope of the business system: a fact about a state change. Events act as both data and as a means of asynchronous communication between services. %%(Source: L9 slides 5–6.)%% |  |
| [**Initiating event**](chapters/week-09-event-driven-architecture.html) | **Initiating event** — an event that originates from an end user and typically kicks off a business process. %%(Source: L9 slide 7.)%% |  |
| [**Derived event**](chapters/week-09-event-driven-architecture.html) | **Derived event** — an internal event generated in response to an initiating event: a software component responds to the initiating event and in turn broadcasts what it did to the rest of the system, within the scope of that initiating event. %%(Source: L9 slide 8.)%% |  |
| [**Command**](chapters/week-09-event-driven-architecture.html) | **Command** — a request for an action to be performed, expressed as intent in the imperative mood (e.g., `ChargeCard`) and sent to a specific receiver; it changes application state and returns no data. %%(Source: L8 slides 4, 25; L9 slide 9.)%% |  |
| [**Query**](chapters/week-09-event-driven-architecture.html) | **Query** — a request that asks for the current state and needs a reply, but does not change state (e.g., `GetBalance`). %%(Source: L9 slide 9.)%% |  |
| [**Event notification**](chapters/week-09-event-driven-architecture.html) | **Event notification** — an event in its "something happened" role: it carries only a small amount of data, and consumers that need more must obtain it from the source. One of the four views of an event. %%(Source: L9 slide 5, from Fowler; Quiz 4 Q3.)%% |  |
| [**Event-carried state transfer**](chapters/week-09-event-driven-architecture.html) | **Event-carried state transfer** — an event in its "here is the data" role: the event carries the data consumers need, so they can work without calling the producer back. The other content-side view of an event. %%(Source: L9 slide 5, from Fowler.)%% |  |
| [**Fire-and-forget communication**](chapters/week-09-event-driven-architecture.html) | **Fire-and-forget communication** — asynchronous communication in which the sender broadcasts information and moves on: it does not wait for a response, nor does it care whether the other components are available. %%(Source: L9 slide 13.)%% |  |
| [**Event-driven architecture**](chapters/week-09-event-driven-architecture.html) | **Event-driven architecture (EDA)** — a software architectural design pattern in which decoupled applications (or components) asynchronously communicate by issuing and consuming events via an event broker; communication is through events, and events drive the system. %%(Source: L9 slides 20, 23.)%% |  |
| [**Event broker**](chapters/week-09-event-driven-architecture.html) | **Event broker** (aka event bus) — an intermediary that receives events from producers, holds them (in queues or partitions), and provides them to consumers that subscribe to topics of interest. It facilitates loose coupling: producers and consumers need not know each other's identity or location. %%(Source: L9 slides 21–23.)%% |  |
| [**Publish–subscribe**](chapters/week-09-event-driven-architecture.html) | **Publish–subscribe (pub/sub)** — a messaging pattern following the event-driven structure: event producers are publishers, event consumers are subscribers, and a broker delivers published events to every subscriber of the topic (e.g., Kafka pub/sub). %%(Source: L9 slide 24.)%% |  |
| [**Event stream**](chapters/week-09-event-driven-architecture.html) | **Event stream** — a partitioned, append-only sequence of related events published by one producing microservice, the owner of every event on that stream; consumers read it sequentially using offsets. %%(Source: L9 slides 32, 35–38.)%% |  |
| [**Event-driven microservice**](chapters/week-09-event-driven-architecture.html) | **Event-driven microservice** — a small application built to fulfill a specific bounded context that communicates by consuming events from one or more input event streams and producing events to other output event streams. %%(Source: L9 slides 32, 42.)%% |  |

#### Week 10 — Asynchronous Communication

| Term | Definition | Source |
|---|---|---|
| [**Synchronous communication**](chapters/week-10-asynchronous-communication.html) | **Synchronous communication** (request–reply) — components or services exchange information at the same time: the sender sends a request and waits for the receiver's response before doing anything else. It couples sender and receiver tightly, adds connection overhead, and leaves failure handling to the sender. %%(Source: L10 slide 5.)%% |  |
| [**Asynchronous communication**](chapters/week-10-asynchronous-communication.html) | **Asynchronous communication** — communication that has a lag between when a message is sent and when the receiver receives, interprets, or responds to it. It enables the independent functioning of sender and receiver and one-to-many sends, coupling them loosely — at the price of needing notification handling. %%(Source: L10 slide 5.)%% |  |
| [**Message**](chapters/week-10-asynchronous-communication.html) | **Message** — a construct carrying a *request to be executed* by another service: a command (perform some action) or a query (get some data), sent point-to-point to exactly one receiver. Intent — not wire format — is what distinguishes a message from an event. %%(Source: L10 slides 12–13.)%% |  |
| [**Topic**](chapters/week-10-asynchronous-communication.html) | **Topic** — a broker channel that enables one-to-many communication, reaching multiple subscribers simultaneously. Within a single partition, processing order is maintained through a unique offset per event; with multiple partitions, receive order may differ from send order. %%(Source: L10 slide 14.)%% |  |
| [**Queue**](chapters/week-10-asynchronous-communication.html) | **Queue** — a broker channel that buffers messages for a single receiver: it follows first-in-first-out, each message is consumed by exactly one receiver, and messages are not copied to other receivers. %%(Source: L10 slides 14, 24.)%% |  |
| [**Persistent communication**](chapters/week-10-asynchronous-communication.html) | **Persistent communication** (aka store-and-forward delivery) — messages are stored at each intermediate hop along the way until the next node is ready to take delivery; the message survives sender or receiver inactivity. E.g., email systems. %%(Source: L10 slide 32.)%% |  |
| [**Transient communication**](chapters/week-10-asynchronous-communication.html) | **Transient communication** — messages are buffered only for small periods of time (as long as the sending/receiving applications are executing); if the message cannot be delivered or the next host is down, it is discarded. Sender and receiver must both be active. E.g., a typical network router (general TCP/IP communication). %%(Source: L10 slide 32.)%% |  |

#### Week 11 — Messaging

| Term | Definition | Source |
|---|---|---|
| [**Message construction**](chapters/week-11-messaging.html) | **Message construction** is the choice of what a message should contain and what the receiver should do with it. The three payload kinds are the **command message** (tells the receiver to do something), the **document message** (gives the receiver data to process) and the **event message** (notifies the receiver that something has happened). | L11 slides 16–18; Enterprise Integration Patterns, eaipatterns.com |
| [**Pipes and filters**](chapters/week-11-messaging.html) | **Pipes and filters** is a message-flow pattern that connects single-purpose processing steps (*filters*) with message channels (*pipes*): each filter consumes a message, performs one transformation or routing decision, and passes the result to the next filter. A splitter feeding a content-based router feeding an aggregator is a pipes-and-filters flow. | L11 slides 15, 46–51; Enterprise Integration Patterns, eaipatterns.com |
| [**Content filter**](chapters/week-11-messaging.html) | **Content filter** is a message-transformation pattern that removes data items the receiver does not need from a message before passing it on, so that each message carries only what its consumer requires. | L11 slide 15 (pattern map); Enterprise Integration Patterns, eaipatterns.com |
| [**Content enricher**](chapters/week-11-messaging.html) | **Content enricher** is a message-transformation pattern that adds data items a message needs but does not carry, typically by looking them up from another source, before passing the message on. | L11 slide 15 (pattern map); Enterprise Integration Patterns, eaipatterns.com |
| [**Request-reply**](chapters/week-11-messaging.html) | **Request-reply** is an asynchronous messaging pattern in which a requestor sends a request message on one channel — carrying a *return address* saying where the reply should go — and later matches the reply message to the request using a *correlation identifier*, instead of blocking on a synchronous call. | L11 slides 20–25; Enterprise Integration Patterns, eaipatterns.com |

#### Week 12 — Scalability

| Term | Definition | Source |
|---|---|---|
| [**Scalability**](chapters/week-12-scalability.html) | **Scalability** is the property of a system to handle a growing amount of work by adding resources to the system. The growth may be in requests processed per time window or in the amount of data managed, while response times stay stable and consistent. | L12 slides 4–6; recap of L3, slide 3 |
| [**Vertical scaling**](chapters/week-12-scalability.html) | **Vertical scaling (scale up)** adds capability to the machines a system is deployed on — e.g. more CPU or memory on the same node — without adding more nodes. It is simple but capped by the hardware limits of a single machine. | L12 slides 3, 11 |
| [**Horizontal scaling**](chapters/week-12-scalability.html) | **Horizontal scaling (scale out)** adds additional machines (nodes) running copies of the service, so that requests are distributed across the replicas. With N replicas and R requests, each server processes about R/N requests. | L12 slides 3, 12 |
| [**Load balancing**](chapters/week-12-scalability.html) | **Load balancing** sends all user requests to a component that chooses which service replica will process each request — aiming to keep every replica equally busy — and relays the responses back to the clients. | L12 slide 13 |
| [**Stateless service**](chapters/week-12-scalability.html) | **Stateless service** is a service whose API implementation retains no state associated with an individual client's session, so any replica can process any request. Session state is kept in a shared session store that every replica can access, which is what makes stateless services cheap to replicate. | L12 slide 14 |
